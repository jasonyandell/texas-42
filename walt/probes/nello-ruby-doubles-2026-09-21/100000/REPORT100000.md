# Ruby's doubles: 100,000-world panel

EXPLORATORY. This is the approved 100,000-world rerun of both retained Ruby
positions, with seeds 1–8 at each position. It uses the same WASM backend and
own/public requests as the earlier panels, with a fresh Node process per case so
high-water memory is released between cases.

## Method and provenance

The shipped WASM and checked-in source remain unchanged. A temporary source copy
changed exactly these validation limits:

```text
walt/walt-player/src/lib.rs:
  worlds 1..=640 -> 1..=100000; budget_ms 100..=20000 -> 100..=240000
walt/walt/src/solver/partnership_wire.rs:
  n > 640 -> n > 100000; budget_ms > 20000 -> > 240000
```

No solver algorithm, game source, or deployment artifact changed. The cap/time
patch is retained in `adapter-cap-time.patch`. The research WASM is
`walt-player-100000.wasm`, SHA-256
`f573f5fc65bd7e0bec788b7e96c555b83a0d304e87f8f80db1897c7f23ac30b1`.
The shipped WASM SHA-256 remains
`fe22d2d24c33e98327799e2e08972481b4e1ec4e48f40256b22b32d0ccd76398`.
Source hashes and the full configuration are in `summary100000.json`.

Every 100,000 call used `n0=8`, baseline fixed selection, modeled fixed
selection, `inner_belief=Voidless`, no partner review, original seed mixing, and
a 240,000 ms decision budget. The initial ply-6 seed-1 pilot completed in
63.05 s. Its peak WASM linear memory was 1,536,491,520 bytes and peak observed
RSS was 1,606,860,800 bytes. The `memory_pressure -Q` availability metric was
88% both before and after; this is not a literal free-RAM percentage. Host
memory pressure stayed healthy and swap remained unused. The largest observed
WASM allocation stayed below 2 GiB,
so no signed-offset ABI workaround was needed.

The two representative 10,000-world checks on this new cap/time build (seed 1
at both positions) matched the retained 10,000 panel's exact rational option
vectors and choices. The full 100,000 panel then completed all 16 cases with
`outer_worlds=100000`, `outer_draw_attempts=100000`, and every phase marked
`completed`.

Each case ran in its own `run_capped.py` watchdog invocation with a 295-second
allowance. Successful build and parity receipts are
`../100000-build-1/run.json`, `../100000-run-parity10k-ply6-seed1/run.json`,
and `../100000-run-parity10k-ply9-seed1/run.json`. The 16 case receipts are the
`../100000-run-*` directories. The aggregate raw panel is `panel100000.json`;
per-case raw requests, checkpoints, exact responses, RSS observations, and
memory-pressure observations are under `cases/`.

Three early command-path typos produced no case output; their failed watchdog
receipts are preserved under `failed-command-receipts/` and excluded from the
16-case timing sums.

The summed standalone case wall timings are 556.692 s (9:16.7). Summing the
16 watchdog wall receipts gives 558.244 s (9:18.2); the difference is process
startup and watchdog overhead. All cases stayed under the 240-second decision
budget and the 295-second watchdog. The memory numbers are per-case WASM linear
memory and observed Node RSS, not phone measurements; the fresh-process design
prevents accumulation across cases.
