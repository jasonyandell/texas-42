# walt2.wasm — the level-2 seat for the browser

walt2 as a WebAssembly decision oracle: bid, declare, and play decisions
for straight points-and-marks Texas 42. The level-2 sibling of
`walt.wasm`: the same outer belief sampling, but every opponent and
partner inside a sampled world is a modeled **level-1 mind** — a mind
that itself samples worlds and reasons about what it cannot see —
instead of a level-0 mind. The oracle prices your options against
opponents it imagines *thinking*. Exact rationals, no floats, no clocks
in the value path. **Exploratory tier** — sampled estimates, never
receipts.

This directory is the whole handoff:

| file | what |
| --- | --- |
| `walt2.wasm` | the solver (~280 KB, zero imports, no JS glue needed) — GENERATED by `../build.sh`, never hand-edited |
| `walt2.ts` | typed wrapper: `Walt2.load()`, `play()`, `bid()`, `declare()`, tile converters |
| `README.md` | this guide |

Verified by `../smoke.mjs`: a full hand driven through this exact binary
reproduces the native Rust test trace play-for-play (the solver is
deterministic per information state — same request, same bytes, native or
wasm, any platform).

## What is and isn't level 2 here

- **`play` is level 2.** Outer worlds are drawn exactly as walt.wasm
  draws them (same sampler, same seed formula — the two oracles price
  the same request over the *same* worlds, common random numbers across
  levels), and the solver's field seats run `Field::Level(1)` with
  `n_inner = [n0, n1]`.
- **`bid` and `declare` are the walt-1 rules, byte-identical to
  walt.wasm's** — enforced by a native equality test. The auction sees
  an empty record (nothing observed yet to anticipate from), and nine
  level-2 declaration pricings are not phone-affordable. A client may
  freely use walt.wasm for the auction and walt2.wasm for the play; the
  answers are identical by construction.

## Quick start (plunge)

Copy `walt2.wasm` + `walt2.ts` into the client (e.g. `src/ai/walt2/`).
The ABI export names are identical to walt.wasm's, so the worker pattern
is the same file with two renames — and the two oracles are separate
wasm modules in separate workers, they never collide:

```ts
// src/ai/walt2/worker.ts
import { Walt2 } from './walt2';
import wasmUrl from './walt2.wasm?url'; // vite: served as an asset

const walt2 = await Walt2.load(fetch(wasmUrl));
self.onmessage = (e) => {
  const { id, kind, req } = e.data;
  try {
    const resp =
      kind === 'play' ? walt2.play(req)
      : kind === 'bid' ? walt2.bid(req)
      : walt2.declare(req);
    self.postMessage({ id, resp });
  } catch (err) {
    self.postMessage({ id, error: String(err) });
  }
};
```

Request mapping (seats, tiles, `decl`/`bid`/`hand`/`plays`/`bidder`/
`seed`, out-of-scope fallback) is identical to walt.wasm's — see its
README; everything there applies verbatim. The one new request knob is
`n1`. The one new response field is `level: 2`.

## Latency — read this before picking knobs

Level-2 cost grows roughly with `n * n1`. Measured trick-1 decisions
(the hardest regime; single-threaded wasm under Node on an M-series —
expect a phone to run ~2-3× slower; later tricks fall to milliseconds):

| n | n1 | n0 | trick-1 decisions observed |
| --- | --- | --- | --- |
| 4 | 2 | 2 | 0.5s / 3.6s / 1.4s / 0s |
| 8 | 2 | 2 | 3.8s / 1.6s / 0s / 0s |
| 8 | 4 | 2 | 6.3s / 10.1s / 2.1s / 0s |
| 16 | 4 | 2 | 13.0s / 1.2s / 0s / 2.9s |
| 16 | 8 | 2 | 26.0s / 11.9s / 7.2s / 0s |

Single-shot instrument readings, not statistics; the spread within a
row is real (the saturation-tie refinement re-evaluates persistent ties
on ×4-to-×16 larger samples when values saturate). Defaults are
**n=8, n1=4, n0=2** — a deliberate "thinks for a bit" setting; tune down
to (4, 2, 2) for snappy play, up when the wait is worth it. `budgetMs`
is inert in wasm: budget by knobs, and put a UI affordance on the wait
("walt is thinking" — plunge's existing slow-seat note and pre-warm
pattern already handle exactly this).

Whether small-knob level 2 beats big-knob level 1 is an empirical
question the client's strength ladder should answer head-to-head — do
not assume depth beats samples at equal latency.

## Conformance assertion (do this)

Every `play` response carries walt2's independently derived `leader` and
`points` (teams `[0&2, 1&3]`). Assert them against your engine on every
decision — two independent rules engines agreeing on every replay is the
cheap, permanent cross-check.

## Regenerating

`../build.sh` — rebuilds `walt2.wasm` from the workspace source
(`rustup target add wasm32-unknown-unknown` once), re-runs the smoke
against the native trace, and refreshes this directory's binary.
